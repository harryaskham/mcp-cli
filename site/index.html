mcp-cli

Rust crates for command-line tools that agents can also call. mcp-cli-core runs one typed command either as a CLI that prints a JSON envelope or as a tool on an MCP server over stdio. Four companion crates add the rest of what such a tool needs: configuration, self-update, feedback reporting and a daemon with a shared cache.

Nine of the tools on a.skh.am/tools depend on at least one of them. Each crate is consumed as a Git dependency; the package is mcp-cli-core because mcp-cli on crates.io is an unrelated project, but the library keeps the name mcp_cli.

mcp-cli-core

One command, two surfaces

The output below comes from a small host in this repository (scripts/site/demo): three tools, math_add, math_divide, which refuses to divide by zero, and crash, which panics.

fn router() -> ToolRouter<()> {
    let mut r = ToolRouter::new();
    r.add_typed_tool("math_add", "Add two integers.", |(), p: Pair| add(p));
    r.add_typed_tool("math_divide", "Divide one integer by another.", |(), p: Pair| divide(p));
    r.add_typed_tool("crash", "Panic, to show how a failing tool is reported.", |(), _: Pair| -> Result<Answer, MathError> {
        panic!("this tool always panics")
    });
    r
}

fn main() {
    let args: Vec<String> = std::env::args().skip(1).collect();
    let pair = |a: &[String]| Pair { lhs: a[0].parse().unwrap(), rhs: a[1].parse().unwrap() };
    match args.first().map(String::as_str) {
        Some("add") => write_json_result(std::io::stdout(), add(pair(&args[1..]))).unwrap(),
        Some("divide") => write_json_result(std::io::stdout(), divide(pair(&args[1..]))).unwrap(),
        Some("mcp") => {
            let config = StdioServerConfig { server_name: "demo".to_owned(), server_version: "0.1.0".to_owned() };
            McpServer::new(config, router()).serve_stdio(&()).unwrap();
        }
        _ => eprintln!("usage: demo add A B | demo divide A B | demo mcp"),
    }
}

Errors are data

A handler's error implements StructuredError: a category, a stable code and a message. Categories are fixed: validation, unsupported_capability, missing_permission, target_not_found, platform_adapter_failure, execution_failure, config_error, serialization_error and timeout, so a client can act on the category without parsing messages.

Bad input keeps the session alive

What the server does, as in the session above
a frame that is not JSONJSON-RPC -32700, id: null
an unknown method-32601
params that don't deserialize-32602
arguments of the wrong typea tool error, invalid_tool_arguments
a handler's own errorisError: true with its code
a handler that panicstool_panicked; later requests still served
a frame over 16 MiBdiscarded to the next newline, -32700
a JSON arraya batch: one array of replies, notifications omitted

Frames are newline-delimited JSON, and the server negotiates protocol versions 2024-11-05, 2025-03-26 and 2025-06-18. Tool registration panics at startup on an empty or duplicate name, or an input type whose schema is not an object, because those are programming errors better caught before any client connects; try_add_tool reports them as values for tool sets assembled at run time.

stdout belongs to the protocol. Anything else that reaches it, such as a println! in a handler, a logger on its default sink or a panic hook redirected to stdout, arrives at the client as a corrupt frame, and many clients drop the session. Send everything else to stderr; the crate cannot enforce it without unsafe, which it forbids.

The companion crates

configurable-cli: one config file, done properly

A host provides one serde and schemars type and a small ConfigSpec. The crate finds ~/.config/<app>/config.yaml by a fixed precedence (an explicit path, $APP_CONFIG, $XDG_CONFIG_HOME, then $HOME), fills defaults for absent or partial files, validates, and writes owner-only (0600) files atomically, following relative or multi-hop symlinks to replace the real target. It supplies the config show | path | status | init | validate | schema | export | import subcommands and matching MCP tools; the ones that change files refuse unless called with confirmed: true.

updatable-cli: replacing a running binary

For tools shipped as binaries through GitHub releases. update finds the newest release that actually has an asset for this platform, stages it as <tool>_next and checks its sha256; a hook early in main promotes it on the next start. feedback-cli: errors and timings, back to the project

A host builds the crate in and exposes a FeedbackConfig in its own configuration; the configured strategy decides where events go, so a project can switch backends without changing code: webhook (POST each event as JSON, optionally with a bearer token read from an environment variable, synchronously or in the background), caco_cli (the local Cacophony CLI), file (JSON lines), stderr (the default) or disabled. Any StructuredError can be reported in one call.

remote-cli: one daemon owns the data

For tools that read from a slow or rate-limited API from many processes. One daemon collects and publishes typed snapshots; every CLI or MCP process subscribes, so only one process talks to the upstream API.

Request headers and bodies have separate limits (16 KiB and 1 MiB by default): oversized headers get 431, an oversized declared body 413 before it is read, and authentication is checked before the rest of a body is accepted. A delayed writer can never overwrite a newer revision. The flake exports lib.mkDaemonModules, which generates matching NixOS, nix-darwin and Nix-on-Droid service modules for any host following the crate's command-line contract.
